# 反编译与破解的真实边界

> 公开文档：**只保留结论，不写操作步骤**。
> 写成操作手册等于递刀；但"我们的客户端坚不可摧"同样是假话，
> 维护者必须清楚边界在哪，才不会被自己的乐观估计误导。

## 一、结论先行

**不存在让客户端校验不可绕过的方案。**

校验发生在用户机器上，用户拥有那台机器。任何声称「客户端反编译加固到
无法破解」的说法都是夸大。

## 二、逐项分析

| 攻击目标 | 实际难度 | 结论 |
|---|---|---|
| 伪造激活码（做注册机） | **不可行** | RS256 私钥从不出现在任何客户端产物里。改用 HS256 也不行 —— 那时公钥就是 HMAC 密钥，而公钥是公开的 |
| 绕过激活用全部防护 | **低** | 流量路径上只有引擎一个校验点，改动一处判断即可（具体入口不在此列出）。这是"客户端校验"的固有上限，不是实现缺陷 |
| 突破一码一机 | **低-中** | 机器码是「规格型」标识（硬件规格拼哈希），同型号机器会得到相同机器码 |
| 读懂检测判据 | **中** | 判据以明文存在于二进制。这是检测类产品的固有暴露面 |

## 三、为什么改用 HS256 也救不了

直觉上「换成对称签名就没人能伪造了」——错。

HS256 的签名密钥 = HMAC 密钥。而验签方（客户端）必须持有它。
客户端持有的任何东西，反编译者都能拿到。所以 HS256 下公钥即私钥，
**签发逻辑会随反编译一起暴露**。

RS256 的不可逆性来自：私钥只在签发方，从未进入任何客户端产物。
这是架构级选择，不是加密强度问题。

## 四、护栏密钥

`config.py` 里原本有两处硬编码明文 fallback 密钥
（`shell_key` / `mapping_key`），只在 `XUANDUN_REQUIRE_SECURE_KEY=1` 时被拒绝 ——
个人版打包时没有设这个变量，等于把公开密钥打进二进制。

现已改为构建期随机生成（`build_secrets.json`，每次构建由
`secrets.token_urlsafe(32)` 重新生成，且被 `.gitignore` 排除）。

**但这也不是绝对防线** —— 密钥仍随包分发。抬高的是门槛，不是消除风险。

`decompile_audit`（签发工具链的一部分，不随本仓库分发）会在发布前
静态检查产物里是否残留这些值。

## 五、真正有效的防护在哪里

客户端校验防不住破解（校验发生在用户机器上，用户拥有那台机器）。
真正有效的防护在两处：

### 1. 不可逆的部分

RS256 私钥不在客户端 —— 这一点改代码也没用。

### 2. 签发方流程管控

这是**唯一能看见「码是否在被传播」的地方**：

- 换机必须走签发方换绑 → 每次换绑都在日志留痕
- jti + 代次可吊销 → 泄露的码能单独作废
- `audit` 子命令检测传播：同一码绑定多台机器 / 换绑多次即告警
  （签发工具链的一部分，不随本仓库分发）

**为什么阈值默认是 2**：正常用户一年可能换一次机（换硬盘、系统重装）。
阈值定太低会把正常用户报成异常，报了也没人看 ——
**一个永远在报警的告警等于没有告警**。

`audit` 只读不写：看到异常不会自动吊销（阈值本就有误报可能，
自动吊销会误伤正常用户），处置由签发方决定。

## 六、给维护者的提醒

新增检测判据时，不要把判据文本当作秘密 —— 它一定会出现在产物里。
真正要守住的是：

1. 私钥不进客户端（架构级，改代码无法破坏）
2. 换机走签发方（留下痕迹）
3. 传播检测的阈值合理（别让告警失效）
