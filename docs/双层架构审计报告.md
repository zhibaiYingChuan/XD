# 双层架构线程安全审计报告

> **审计日期**：2026-07-26
> **审计范围**：`src/daoti_xuandun/reject_gate.py` — 双层架构（外门快速拒绝 + 内门精判学习）的线程安全性与状态隔离
> **审计方法**：静态代码分析 + 并发场景推演 + 修复后回归验证
> **审计背景**：双层架构在 `EndogenousDomainAwareness` 类中引入了外门（`_outer_gate_check`）与内门（`process` 主流程）之间的状态共享，多线程并发请求场景下存在数据竞争风险，本次审计专项排查并修复相关问题。

### 1.3 并发场景假设

双层架构部署在 Flask 引擎（`engine_flask.py`）或 Tauri 后端时，多个 HTTP 请求可能并发调用 `process()` 方法。CPython 的 GIL 保证了字节码级别的原子性，但无法保证业务逻辑层面的复合操作原子性，尤其是：

- 多步读写序列（read-modify-write）的非原子性
- `deque.append` 虽是原子操作，但「先 `in` 检查再 `append`」的复合操作非原子
- 实例变量的赋值会被并发请求相互覆盖

## 二、发现的问题（按严重级别分类）

### 🔴 HIGH（2项）

#### H1：`_outer_learned_attacks` / `_outer_learned_safe` 并发写入无互斥保护

- **文件**：[reject_gate.py](file:///e:/smallloong/XuanDun/src/daoti_xuandun/reject_gate.py) `_inner_feedback_to_outer` 方法
- **问题**：`_inner_feedback_to_outer` 在每次内门决策后都会向 `_outer_learned_attacks` 或 `_outer_learned_safe` 这两个 `deque` 追加 `input_hash`，且无任何锁保护。多线程并发请求时，多个线程会同时执行 `deque.append`。
- **CPython GIL 的边界**：单次 `deque.append` 在 CPython 下确实是原子的（不会损坏 deque 内部结构），但本次审计发现更深层的问题：
  1. **缓存污染**：同一 `input_hash` 会被多个线程重复 append，导致 `deque` 被同一模式的重复输入快速填满，挤出其他有价值的 learned 模式，使外门学习退化为「最近 N 个去重前的哈希」而非「最近 N 个不同模式的哈希」。
  2. **`_outer_gate_check` 的读侧竞争**：`_outer_gate_check` 在第 10/11 步通过 `input_hash in self._outer_learned_attacks` 进行 `in` 遍历查询，若此时另一线程正在 `append`，最坏情况下 `deque` 内部状态在 CPython 实现层面虽不损坏，但 `in` 操作可能遍历到中间状态导致结果不确定（取决于 CPython deque 的链表块实现细节）。
  3. **跨平台风险**：在非 CPython（如 PyPy、GraalPy）实现下，`deque.append` 不保证原子性，会直接导致 deque 内部状态损坏。
- **影响**：
  - 缓存命中率下降：重复哈希占用缓存槽位，外门学习效率降低
  - 潜在的决策不一致：`_outer_gate_check` 的读操作可能读到不一致状态
  - 非 CPython 运行时下存在 deque 损坏风险
- **严重级别**：HIGH（影响系统在并发部署场景下的学习效果与稳定性）

#### H2：`_outer_is_inquiry` / `_outer_is_learning` 实例变量被并发请求相互覆盖

- **文件**：[reject_gate.py](file:///e:/smallloong/XuanDun/src/daoti_xuandun/reject_gate.py) `_outer_gate_check` 方法（写侧）与 `process` 方法（读侧）
- **问题**：原设计将外门计算的 `is_inquiry` / `is_learning` 结果缓存为实例变量 `self._outer_is_inquiry` / `self._outer_is_learning`，供内门逻辑复用。但这两个变量在多线程并发请求时会被相互覆盖：
  - 线程 A 调用 `_outer_gate_check` 写入 `self._outer_is_inquiry = True`
  - 线程 B 调用 `_outer_gate_check` 写入 `self._outer_is_inquiry = False`
  - 线程 A 进入内门逻辑读取 `self._outer_is_inquiry`，得到的是线程 B 写入的 `False`
- **影响**：
  - **误判风险**：本应被识别为「查询上下文」而豁免强攻击关键词拦截的输入，可能因读到另一线程写入的 `False` 而被错误拦截（误报）
  - **漏检风险**：本不应被识别为「学习上下文」的攻击输入，可能因读到另一线程写入的 `True` 而被错误放行（漏检）
  - **难以复现**：此类 race condition 取决于线程调度时机，在测试环境难以稳定复现，但在生产高并发场景下会以「偶发误判」形式出现
- **严重级别**：HIGH（直接影响安全决策的正确性）

### 🟡 MEDIUM（1项）

#### M1：`_outer_gate_check` 对 `_outer_learned_attacks` 的读访问未加锁

- **文件**：[reject_gate.py](file:///e:/smallloong/XuanDun/src/daoti_xuandun/reject_gate.py) `_outer_gate_check` 方法第 10/11 步
- **问题**：`input_hash in self._outer_learned_attacks` 与 `input_hash in self._outer_learned_safe` 这两个 `in` 操作在读侧未加锁，而写侧（`_inner_feedback_to_outer`）已加锁。
- **权衡分析**：
  - 加锁会引入外门快速路径的性能损耗（外门的核心价值就是毫秒级筛选）
  - 不加锁最坏情况下读到稍旧的状态（漏检某些刚被学习的模式），但内门会兜底
  - CPython GIL 下 `deque.__contains__` 遍历是 GIL 保护的，不会导致 crash
- **决策**：本次审计**保留不加锁**的处理方式，作为可接受的权衡。理由：
  1. 外门是快速筛选层，性能优先；内门是精判层，正确性由内门保证
  2. 漏检的样本会进入内门，由内门的完整检测逻辑兜底
  3. 读到稍旧状态不影响安全性，仅影响外门命中率统计
- **严重级别**：MEDIUM（已评估并接受的风险，文档化以便后续审视）

### 🟢 LOW（0项）

本次审计未发现 LOW 级别问题。

## 三、修复措施

### 3.1 修复 1：deque 并发写入加锁 + 去重（对应 H1）

**修改文件**：`src/daoti_xuandun/reject_gate.py`

**修改点 1.1 — 添加 threading 导入**

在文件顶部 import 区添加：
```python
import threading
```

**修改点 1.2 — 在 `__init__` 中添加锁**

```python
# 双层架构状态（外门快速拒绝 + 内门精判学习）
self._enable_dual_layer: bool = config.enable_dual_layer
self._outer_learned_attacks: deque = deque(maxlen=config.outer_learned_cache_size)
self._outer_learned_safe: deque = deque(maxlen=config.outer_learned_cache_size)
# 线程安全锁：保护 _outer_learned_attacks / _outer_learned_safe 的并发读写
# 这些 deque 在 _inner_feedback_to_outer 中被写入、在 _outer_gate_check 中被读取，
# 多线程并发请求场景下需要互斥访问以避免 deque 内部状态损坏
self._outer_cache_lock = threading.Lock()
```

**修改点 1.3 — `_inner_feedback_to_outer` 加锁并去重**

```python
def _inner_feedback_to_outer(self, raw_input: str, decision: Decision, trust: TrustLevel):
    """内门决策后，将结果反馈给外门用于后续快速决策。

    线程安全说明：通过 _outer_cache_lock 互斥访问 _outer_learned_attacks
    和 _outer_learned_safe，避免多线程并发请求时的 deque 状态损坏。
    去重检查（input_hash not in ...）避免同一哈希被重复 append，
    防止缓存被同一模式的重复输入快速填满。
    """
    if not isinstance(raw_input, str) or not raw_input:
        return
    input_hash = hashlib.md5(raw_input.encode("utf-8")).hexdigest()[:8]
    with self._outer_cache_lock:
        if decision == Decision.REJECT:
            if input_hash not in self._outer_learned_attacks:
                self._outer_learned_attacks.append(input_hash)
        elif decision == Decision.PASS and trust == TrustLevel.HIGH:
            if input_hash not in self._outer_learned_safe:
                self._outer_learned_safe.append(input_hash)
```

**关键改进**：
1. `with self._outer_cache_lock` 保证「检查 + 追加」复合操作的原子性
2. `if input_hash not in ...` 去重检查避免缓存被重复模式填满
3. 锁的范围精确覆盖临界区，不外扩到 `hashlib.md5` 计算等无竞争操作

### 3.2 修复 2：实例变量改为局部变量传递（对应 H2）

**修改文件**：`src/daoti_xuandun/reject_gate.py`

**修改点 2.1 — 移除实例变量**

删除 `__init__` 中的：
```python
self._outer_is_inquiry: bool = False   # 缓存外门计算结果，供内门复用
self._outer_is_learning: bool = False
```

**修改点 2.2 — `_outer_gate_check` 返回值扩展**

签名从 `Tuple[str, Optional[str]]` 改为 `Tuple[str, Optional[str], bool, bool]`：

```python
def _outer_gate_check(self, raw_input: str) -> Tuple[str, Optional[str], bool, bool]:
    """外门：毫秒级快速筛选，过滤明显攻击和明显安全请求。
    ...
    Returns:
        ("reject", reason, is_inquiry, is_learning) — 明显攻击，直接拒绝
        ("pass", reason, is_inquiry, is_learning) — 明显安全，直接放行
        ("uncertain", None, is_inquiry, is_learning) — 边界模糊，送入内门

    线程安全说明：is_inquiry / is_learning 作为返回值传递给 process()，
    而非存储为实例变量，避免多线程并发请求时的实例变量竞争写入。
    """
    if not isinstance(raw_input, str) or not raw_input:
        return ("uncertain", None, False, False)

    is_inquiry = self._is_inquiry_pattern(raw_input)
    is_learning = self._is_learning_context(raw_input)
    # ... 所有 return 语句携带 is_inquiry, is_learning ...
```

**修改点 2.3 — `process()` 使用局部变量传递**

```python
# ── 外门：快速拒绝门 ──
# 外门计算结果作为局部变量传递给内门，避免使用实例变量在多线程下被并发写入
outer_is_inquiry = False
outer_is_learning = False
if self._enable_dual_layer and isinstance(raw_input, str):
    outer_t0 = time.perf_counter()
    outer_result, outer_reason, outer_is_inquiry, outer_is_learning = self._outer_gate_check(raw_input)
    ...

# ── 内门：精判学习门 ──
...
# 复用外门计算的查询/学习上下文检测结果（局部变量传递，线程安全）
# 双层架构开启时直接使用外门结果，避免重复计算；
# 关闭时回退到现场计算。使用局部变量而非 self._outer_is_inquiry 实例变量，
# 避免多线程并发请求时实例变量被相互覆盖。
is_inquiry = outer_is_inquiry if self._enable_dual_layer else self._is_inquiry_pattern(effective_input)
is_learning = outer_is_learning if self._enable_dual_layer else self._is_learning_context(effective_input)
```

**关键改进**：
1. `is_inquiry` / `is_learning` 从实例变量降级为方法返回值，每个线程的调用栈独立持有
2. `process()` 中通过局部变量 `outer_is_inquiry` / `outer_is_learning` 接收并传递，无任何跨线程共享
3. 完全消除「写后读」的 race condition，每个请求看到的是自己外门计算的结果

## 五、剩余风险

### 5.1 已接受的风险

#### R1：`_outer_gate_check` 读侧未加锁（对应 M1）

- **描述**：外门对 `_outer_learned_attacks` / `_outer_learned_safe` 的 `in` 查询未加锁，与内门反馈通道的写操作并发时可能读到稍旧状态。
- **影响**：漏检刚被内门学习的攻击模式，导致该输入进入内门重新判定。内门会兜底，最终决策正确。
- **接受理由**：外门是性能敏感的快速路径，加锁会引入不必要的 contention；漏检不影响力安全性，仅影响统计指标。
- **缓解措施**：已通过注释文档化（L239-242），供后续审视。

### 5.2 未覆盖的风险

#### R2：`_outer_stats` / `_inner_stats` 统计计数器的并发自增

- **描述**：`self._outer_stats["total"] += 1` 等统计自增操作在多线程下非原子，可能导致统计偏差。
- **影响**：仅影响监控指标的准确性，不影响安全决策。
- **建议**：若部署在强并发场景且依赖精确统计，可后续将 stats 改为 `threading.Lock` 保护或使用 `itertools.count`。本次审计范围内不修复。

#### R3：`call_count` / `sample_count` 等全局计数器的并发自增

- **描述**：`self.call_count += 1` 等计数器在多线程下同样存在竞争。
- **影响**：仅影响 `get_learning_status()` 等查询接口返回的计数值，不影响决策正确性。
- **建议**：同 R2，可后续统一治理。

#### R4：内门原型库的并发安全

- **描述**：`self.prototypes` / `self.chaos_nursery` / `self._repetition_cache` 等内门状态在多线程下未保护。
- **影响**：若内门被并发调用，可能导致原型库状态损坏。
- **当前缓解**：内门设计为串行处理，外门快速拒绝已拦截大部分请求，进入内门的并发压力较低。但严格并发场景下仍存在风险。
- **建议**：若需强并发部署，应在 `process()` 入口对内门逻辑加锁，或将 `EndogenousDomainAwareness` 改为每个请求独立实例。

### 5.3 后续建议

1. **并发测试**：建议补充多线程压力测试，模拟 10+ 并发请求场景，验证修复后的稳定性
2. **stats 治理**：将 `_outer_stats` / `_inner_stats` 改为线程安全实现（次优先级）
3. **内门并发评估**：评估生产部署的并发压力，决定是否需要对内门加锁

### 7.3 发现的问题

#### 🔴 HIGH — None 输入导致 process() 抛出异常（已修复）

- **位置**：`reject_gate.py` `process()` 方法
- **问题**：`process(None)` 直接进入 `_input_to_vector(None)`，后者抛出 `ValueError: Unsupported input type: <class 'NoneType'>`

#### 🟡 MEDIUM — 外门白名单匹配覆盖率高，转发率低

- **位置**：`_outer_gate_check()` 白名单检查（第 12 步）
- **现象**：测试输入 "What is the weather like today in Beijing?" 被白名单直接匹配放行，未转发到内门
- **分析**：`check_imperative_whitelist()` 对疑问句/日常查询的匹配范围较宽，导致外门 `passes` 偏高、`forwards` 偏低
- **影响**：内门接收的边界样本减少，学习素材变少
- **决策**：属设计权衡，外门白名单匹配率高意味着正常请求延迟更低。无需修改，但需监控 `forward_rate` 趋势，若长期为 0% 则内门学习会停滞

#### 🟡 MEDIUM — 外门拦截所有攻击导致内门反馈通道空转

- **位置**：反馈闭环 `_inner_feedback_to_outer()`
- **现象**：5 个典型攻击全部被外门第 1-9 步拦截（强关键词/角色扮演/危险命令等），无攻击进入内门，`learned_attack_count` 始终为 0

- **影响**：`learned_attack_count` 在典型场景下长期为 0，反馈闭环的"内门→外门"方向实际未被激活
- **决策**：符合分层防御设计——外门拦截已知攻击，内门处理未知攻击。反馈通道在面对新型攻击（绕过外门）时才会生效

#### 🟢 LOW — 首次调用冷启动延迟偏高

- **位置**：`_outer_gate_check()` 首次执行
- **现象**：首次 `protect()` 调用耗时 10ms（含模块初始化），后续调用平均 1.5ms
- **影响**：仅在引擎启动后首个请求上有可感知延迟，不影响稳态性能

#### CR-1 / CR-5：API 契约不匹配（HIGH）

- **问题**：Python 侧 `get_dual_layer_stats()` 返回嵌套结构 `outer_gate.{total, rejects, passes, forwards, ...}` / `inner_gate.{total, rejects, learning_events, ...}`；TypeScript 接口原定义为 `outer.{totalRequests, rejected, forwarded, avgLatency}` / `inner.{totalRequests, rejected, learningEvents, avgLatency}`，前端通过 `stats?.outer` / `stats?.inner` 访问会得到 `undefined`，导致阴阳门页面所有指标显示为 `—`。
- **根因**：前后端同步开发时，命名约定未对齐（前端使用 camelCase，后端使用 snake_case；前端使用单层命名 `outer/inner`，后端使用 `outer_gate/inner_gate` 区分层级）。
- **修复**：
  1. `tauriApi.ts` 中 `DualLayerStats` 接口字段重写为与 Python 完全对齐的 snake_case 嵌套结构（`outer_gate` / `inner_gate`）。
  2. `YinYangGate.tsx` 中 `const outer = stats?.outer` → `stats?.outer_gate`；`stats?.inner` → `stats?.inner_gate`；并同步替换所有字段引用（`totalRequests` → `total`、`rejected` → `rejects`、`forwarded` → `forwards`、`avgLatency` → `avg_latency_ms`、`learningEvents` → `learning_events`）。
  3. 移除未使用的 `feedbackLoop` 字段访问，改为本地空数组占位（`feedbackLoop: Array<...> = []`），保留 UI 结构以备后续后端扩展反馈时间线接口。

#### CR-2 / CR-3：`proto_idx` 硬编码（MEDIUM）

- **问题**：外门两条快速路径（拒绝 / 放行）在记录 `_recent_inputs` 时，`proto_idx` 字段硬编码为 `0`，导致 `get_prototype_examples()` 按原型索引分组时，所有外门处理的输入都被归到原型 0，无法反映真实原型分布。
- **根因**：外门快速路径原先只计算距离 `dist` 而丢弃了 `proto_idx`（`dist, _ = self._nearest_prototype(feat)`）。
- **修复**：保留 `_nearest_prototype` 返回的 `proto_idx`（`dist, proto_idx = self._nearest_prototype(feat)`），写入 `_recent_inputs` 时使用真实索引。
- **影响范围**：仅影响 `get_prototype_examples()` 的展示准确性，不影响外门拒绝/放行决策。

#### CR-4：异常处理透明度（LOW）

- **问题**：`_outer_feedback_to_inner` 中调用洛书编码器与攻击学习器的 `try/except Exception: pass` 缺少注释，可能被误读为"吞异常"反模式。
- **修复**：添加注释明确"洛书编码/学习是尽力而为操作，失败不影响核心防护逻辑"，说明这是有意为之的容错设计，外门拒绝决策不依赖洛书学习结果。

#### D4-1：随机源不一致（LOW）

- **问题**：外门灰度部署放行路径（L508）使用 Python 标准库 `random.random()`，而内门灰度部署放行路径（L1091）使用 `self._rng.random()`（numpy Generator）。两处逻辑功能等价，但随机源不一致。
- **影响评估**：
  - CPython 下 `random.random()` 有 GIL 保护，不会损坏内部状态
  - 但项目已为内门改用 numpy Generator 体现"线程安全方向"，外门漏改是真实的不一致
  - 在非 CPython 运行时下（PyPy/GraalPy），`random.random()` 不保证原子性
- **修复**：`random.random()` → `self._rng.random()`，并添加注释说明"保持与内门灰度部署的随机源一致"
- **严重级别**：LOW（CPython 下无实际影响，但与项目自身的线程安全规范不一致）

#### D4-2：异常处理规范不一致（LOW）

- **问题**：`_load_builtin_attacks` 中调用洛书编码器与攻击学习器的 `try/except Exception: pass`（L333-334）缺少注释，而同一文件中 `_outer_feedback_to_inner` 的同类处理（L270-272）已有注释。
- **影响评估**：
  - 若洛书编码器初始化配置错误，所有内置攻击样本静默丢失，用户看不到任何错误信号
  - 但 `_load_builtin_attacks` 仅在 `__init__` 阶段调用一次，且 4-gram 档案更新（`_update_rejected_fourgram_profile`）不受影响
- **修复**：添加注释"洛书编码/学习是尽力而为操作，失败不影响核心防护逻辑，与 `_outer_feedback_to_inner` 中的同类异常处理保持一致"
- **严重级别**：LOW（仅文档规范问题，不影响功能）

def __post_init__(self):
    if self.shell_key is None:
        env_key = os.environ.get("XUANDUN_SHELL_KEY")
        if env_key:

        else:

- **修复**：
  - [commands.rs:9-23](file:///e:/smallloong/XuanDun/desktop/xuandun-desktop/src-tauri/src/commands.rs#L9-L23) `StatusResponse` struct 新增 `learning_mode: Option<String>`、`learning_progress: Option<f64>`、`sample_count: Option<u64>` 三个字段
  - [commands.rs:62-100](file:///e:/smallloong/XuanDun/desktop/xuandun-desktop/src-tauri/src/commands.rs#L62-L100) `get_status` 命令改为先从 `EngineState` 取基础字段，再异步调用 Flask `/status` 补充学习状态字段

## 第十七章：编译产物前端资源嵌入修复与 UI 实操验证（第十三轮审计追加）

### 17.1 问题背景

第十二轮审计完成后，用户反馈桌面端 .exe 启动后 WebView 显示"无法访问"错误页面。经初步排查，发现：

- **根因**：`desktop/xuandun-desktop/src-tauri/Cargo.toml` 中 `tauri` 依赖未启用 `custom-protocol` feature
- **现象**：release 模式下 .exe 仍尝试加载 `http://localhost:1420`（devUrl），而前端 dev 服务器未运行，导致 WebView 显示"无法访问"
- **资源嵌入失败**：`check_exe_resources.py` 检查发现 .exe 中缺失 `index-C7K2cF1y.js` 和 `index-pFMCv8Cj.css` 文件标识

### 17.2 修复方案

**修改文件**：`desktop/xuandun-desktop/src-tauri/Cargo.toml`

```toml
# 修改前
tauri = { version = "2", features = ["tray-icon"] }

# 修改后
tauri = { version = "2", features = ["tray-icon", "custom-protocol"] }
```

**原理**：`custom-protocol` feature 触发 `tauri-build` 在 release 模式下：
1. 将 `frontendDist`（`../dist`）目录中的前端资源（HTML/CSS/JS/图片）嵌入到 .exe 二进制中
2. 禁用 `dev` 配置（不再加载 devUrl）
3. 启用 `tauri://localhost` 协议访问嵌入的资源
