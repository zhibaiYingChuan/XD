## 一、5W2H 分析

### 1.1 WHAT（核心问题定义）

**当前最大的产品短板：三端形态割裂 + 版本混乱 + 评审印象分不足**

具体表现为三个层次：

| 层次 | 问题 | 严重度 | 影响面 |
|------|------|--------|--------|
| **表层（用户可见）** | Web Demo 版本号 1.2.3 与主线 1.3.0 不一致；CHANGELOG 停更于 1.2.1；Web Demo 尚未实际部署 | 高 | 评审第一印象崩坏——"版本号都对不齐，产品成熟度存疑" |
| **中层（体验层）** | 前端 9 项 P1 未修复（紧急逃生无二次确认/Agent 策略静默吞错/Logs 竞态等）；桌面端缺少"开箱即用"的第一印象 | 中高 | 评审实际体验 Demo 时发现细节瑕疵，拉低评分 |
| **深层（战略层）** | 项目定位是"活性防护 LLM 防火墙"，但对外叙事偏技术术语堆砌；评审无法在 30 秒内理解核心差异化 | 高 | 评审记不住"玄盾和别的方案有什么不同" |

**为什么这是最大的问题？**

项目核心算法评级 A-（十轮审计收敛）、文档体系 A-（38 个文档）、工程质量 A-（PDCA 循环完备），说明**技术底子过硬**。但产品化层面存在三个"致命扣分点"：

1. **评审的第一眼印象**：打开 Web Demo 看到 1.2.3 版本号 → 扣分
2. **评审的动手体验**：Demo 中遇到按钮无响应/加载失败静默吞错 → 扣分
3. **评审的最终记忆**：无法用一句话说清 "玄盾到底比 Guardrails 好在哪里" → 扣分

**结论：当前不是"技术不够好"的问题，而是"产品化包装不够好"的问题。**

### 1.2 WHY（为什么要现在做）

| 驱动力 | 说明 | 紧迫性 |
|--------|------|--------|
| **比赛/评审窗口** | 项目当前处于评审期，评审印象分直接影响最终评级 | ⚡ 高 |
| **版本混乱已造成实际影响** | 审计发现 4 处版本不一致，部署后用户看到过期版本号 | ⚡ 高 |
| **Web Demo 部署就绪但未上线** | 配置已完备，只差手动部署，尚未形成三端闭环 | ⚡ 高 |
| **Node 20 弃用倒计时** | Netlify 构建可能随时中断 | 🟡 中 |
| **单点维护风险** | 核心作者单人维护，引入外部贡献者需要规范化的版本管理 | 🟡 中 |

### 1.3 WHO（目标用户与角色）

| 用户角色 | 画像 | 核心诉求 | 在评审中的权重 |
|----------|------|----------|:------------:|
| **评审打分者（A）** | 比赛评委/技术评审专家 | 快速理解项目价值、验证技术可行性、评估产品成熟度 | 60% |
| **技术决策者（B）** | 金融/医疗企业 CTO、安全负责人 | 确认产品是否满足合规要求、是否可集成、维护成本 | 25% |
| **终端用户（C）** | AI 应用开发者、运维人员 | 开箱即用体验、文档清晰度、问题排查效率 | 15% |

**优先级排序：A > B > C**。本次优化以"评审打分者体验"为第一优先级。

### 1.4 WHEN（时间线）

| 阶段 | 时间 | 目标 | 备注 |
|------|------|------|------|
| **立即行动** | 第 1-3 天 | 修复所有"扣分项"（版本号/P1-01 等） | 不影响评审进程 |
| **短期冲刺** | 第 4-7 天 | Web Demo 部署上线 + 评审叙事重构 | 让评审可以实际体验 |
| **中期优化** | 第 8-14 天 | 修复剩余 P1 问题 + 补充单元测试 | 持续提升评分 |
| **长期规划** | 第 15 天+ | 方向一/二/三（Dashboard/报告/企业集成） | 按原产品迭代规划推进 |

### 1.5 WHERE（优化范围）

| 范围 | 包含 | 不包含 |
|------|------|--------|
| **桌面端前端** | 9 个 P1 问题修复、UI 一致性检查 | 页面重构、新功能开发 |
| **Web Demo** | 版本号统一、实际部署（Render + Netlify） | 功能增强 |
| **文档体系** | CHANGELOG 补写、部署指南升级 | 新文档创建 |
| **对外叙事** | 评审材料包装、"三个一句话"叙事 | 品牌重塑 |
| **CI/CD** | 版本号门禁覆盖 web-demo/gateway | SLSA 升级 |

### 1.6 HOW（如何做）

1. **止血**：修复版本号不一致 + 高优先级 P1（1-3 天）
2. **上線**：Web Demo 部署上线，让评审可以实际体验（1 天）
3. **包装**：重构对外叙事，准备"三个一句话" + 评审材料（1 天）
4. **修补**：修复剩余 P1 问题 + 补充单元测试（7 天）
5. **加固**：版本号门禁扩展 + CHANGELOG 补写 + 部署指南升级（2 天）

## 二、KANO 模型分类

### 2.1 分类方法

针对每个候选功能/修复项，设计正反两个问题：
- **正向**：如果此功能完善，你会觉得？(满意/理应如此/无所谓/可以忍受/不满意)
- **反向**：如果此功能缺失，你会觉得？(满意/理应如此/无所谓/可以忍受/不满意)

基于答案组合，对照 KANO 分类表确定属性。

### 2.2 分类结果

#### Must-be（基本型，不做就扣分）

| 编号 | 功能/修复 | 当前状态 | 评审感知 |
|------|----------|----------|----------|
| M-01 | **版本号统一**（web-demo/gateway → 1.3.0） | 4 处不一致 | "版本号都对不齐，产品管理混乱" |
| M-02 | **CHANGELOG 补写**（1.2.2/1.2.3/1.3.0） | 停在 1.2.1 | "变更不透明，无法追溯" |
| M-03 | **P1-01 紧急逃生二次确认** | 无确认，误触即放行 | "安全产品连基本确认都没有" |
| M-04 | **P1-02 Agent 策略切换 loading** | 静默吞错 | "配置不生效，功能不可靠" |
| M-05 | **P1-06 Logs 加载失败提示** | 误显示"暂无日志" | "数据不可信，排查困难" |
| M-06 | **P1-08 Reports 日期校验** | 无校验 | "基础功能都不完善" |
| M-07 | **P1-09 代理端口校验** | 可输入非法值 | "基本输入校验都没有" |

#### Performance（期望型，做了加分，不做扣分）

| 编号 | 功能/修复 | 当前状态 | 评审感知 |
|------|----------|----------|----------|
| P-01 | **Web Demo 在线部署**（Render + Netlify） | 配置就绪，未部署 | "不能在线体验，缺乏说服力" |
| P-02 | **P1-03 模拟测试并发守卫** | 无 useRef 守卫 | "测试结果不稳定" |
| P-03 | **P1-05 Logs 分页竞态** | 无请求序列号 | "翻页数据错乱" |
| P-04 | **P1-07 学习模式切换确认** | 样本不足无确认 | "提前切换导致误报" |
| P-05 | **P1-04 Dashboard 向导按钮** | 无响应 | "按钮是坏的，体验差" |
| P-06 | **P1-10 灰度滑块防抖** | 频繁触发 API | "拖动卡顿，性能差" |
| P-07 | **P1-11 防护模式竞态** | 快速点击模式不确定 | "模式切换不可靠" |
| P-08 | **部署指南升级 v1.3.0** | 滞后 v1.2.0 | "文档与产品脱节" |

#### Attractive（魅力型，做了惊喜，不做不扣分）

| 编号 | 功能/修复 | 当前状态 | 评审感知 |
|------|----------|----------|----------|
| A-01 | **"三个一句话"叙事重构** | 技术术语堆砌 | 30 秒内理解核心价值，记住"阴阳门" |
| A-02 | **Demo 高光时刻设计**（3 个时刻） | 无专业演示脚本 | 评审印象深刻，主动传播 |
| A-03 | **P1-12 Dashboard 时间范围切换优化** | 无 loading | 图表切换流畅，加分项 |
| A-04 | **P1-13 Detect 文本长度限制** | 无限制 | 防误操作，细节到位 |
| A-05 | **P1-14 Agent 定时刷新不打断编辑** | 刷新重置 select | 编辑体验流畅 |
| A-06 | **P1-16 引擎重启二次确认** | 无确认 | 操作安全，加分项 |
| A-07 | **P1-17 Wizard loading 状态** | 无 loading | 引导流程流畅 |
| A-08 | **B-02 Actions SHA pin** | 未 pin | 供应链安全加分 |

#### Indifferent（无差异型，可暂缓）

| 编号 | 功能/修复 | 理由 |
|------|----------|------|
| I-01 | P1-21 生成密钥 loading | 仅展示性优化，评审不关注 |
| I-02 | P1-22 邮件密码自动填充 | 浏览器兼容性问题，非核心 |
| I-03 | P1-18 帮助中心链接 | 功能规划中，评审不会关注 |
| I-04 | P1-20 键盘可访问性 | 评审场景无需键盘操作 |

### 2.3 Better-Worse 系数分析

```
Better（满意度提升系数） = (A + O) / (A + O + M + I)
Worse（满意度降低系数） = (O + M) / (A + O + M + I) × (-1)
```

| 功能 | Better | Worse | 象限 | 优先级 |
|------|--------|-------|------|--------|
| M-01 版本号统一 | 0.15 | -0.85 | 🟢 Must-be | ⭐⭐⭐⭐⭐ |
| M-03 紧急逃生确认 | 0.20 | -0.80 | 🟢 Must-be | ⭐⭐⭐⭐⭐ |
| A-01 叙事重构 | 0.75 | -0.10 | 🔵 Attractive | ⭐⭐⭐⭐⭐ |
| P-01 Web Demo 部署 | 0.65 | -0.45 | 🟡 Performance | ⭐⭐⭐⭐⭐ |
| P-02 模拟测试守卫 | 0.55 | -0.50 | 🟡 Performance | ⭐⭐⭐⭐ |
| A-02 Demo 高光时刻 | 0.70 | -0.05 | 🔵 Attractive | ⭐⭐⭐⭐ |
| M-02 CHANGELOG 补写 | 0.25 | -0.70 | 🟢 Must-be | ⭐⭐⭐⭐ |
| P-03 Logs 分页竞态 | 0.50 | -0.45 | 🟡 Performance | ⭐⭐⭐⭐ |

**策略结论**：先做 Must-be 止血（消除扣分），再做 Performance 提升（加分），Attractive 中选投入产出比最高的做（叙事重构和 Demo 高光时刻）。

**角色**：评审专家（技术背景，30-45 岁，了解 AI 安全领域）
**目标**：在 30 分钟内理解玄盾的价值、验证技术可行性、评估产品成熟度

## 六、优先级排序的完整修复清单

### 6.1 排序方法

- **R**（Reach）：影响多少评审/用户（1-10）

- **C**（Confidence）：修复效果的可信度（1-10）
- **E**（Effort）：工作量（人天，取倒数）

```
RICE Score = (R × I × C) / Effort
```
