feat(activation): 激活码签发 WebUI

命令行签发要敲一长串参数，其中 32 位十六进制机器码错一位就是给一台
不存在的机器签了码。这个循环每天跑几十次，网页粘贴更可靠。

六个页签覆盖签发全链路：签发 / 换机换绑 / 吊销 / 传播审计 / 签发记录 / 验码。

几个刻意的设计决定：

- 不重写签名逻辑，import gen_activation_keys 复用。两份签名实现一旦漂移，
  WebUI 签出的码会客户端验不过，而这种故障要等用户激活失败才暴露。

- 拒绝绑定非本机地址。--host 0.0.0.0 意味着局域网里任何人都能给自己签发
  永久码；这是最容易被临时调试顺手打开然后忘记关掉的洞。

- 中间件挡住非本机请求。不做鉴权是刻意的：宁可明确「它不防远程」，
  也不要假鉴权给人已经安全的错觉。

- jti / 机器码 / 代次全部从签出的码里解码取得，不解析 CLI 的人读排版。
  回归：曾用 split 冒号 从「jti : a_xxx （不变，吊销仍有效）」切值，
  把括号说明一起带了出来，那个 jti 喂给吊销会静默失败，
  表现是「显示已吊销，实际没吊」。

- 日志读不出来必须报错，不能当成「没有记录」。静默吞掉的话，
  审计会得出「未发现异常传播」，而实际只是文件坏了，
  唯一的传播检测手段失效，界面却显示一切正常。

- 空白用户名拒签（sub 是日后核对用户的唯一依据）。
  pydantic 的 min_length=1 挡不住纯空格。

测试 14 项，用临时密钥对不用仓库真私钥。三个变异点全部被精确捕获。
