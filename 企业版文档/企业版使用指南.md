# 道体·玄盾 企业版使用指南

> 面向对象：企业 IT / 运维 / 安全负责人
> 适用版本：v1.3.5-beta
> 更新日期：2026-09-29

---

## 一句话说明

玄盾企业版是一个**可自我进化的 AI 安全网关**。它以 OpenAI 兼容反向代理的形态接入企业内网的 AI 流量，对**输入提示词**与**模型输出**做实时检测，拦截提示词注入、数据外泄与越权工具调用，并通过 Web 管理控制台集中配置、监控与告警。

与个人版的根本差别：个人版是一台机器上一道安检站；企业版是**一个集群一道安检站**，带集中管控、多租户密钥与审计留痕。

## 一、企业版能解决什么问题

| 风险 | 玄盾的处理方式 |
|------|---------------|
| 员工把公司机密粘贴进公网 AI | 出站流量经网关，检查输入命中敏感信息则阻断 |
| 提示词注入（越狱、系统提示词窃取） | 输入侧检测注入模式，命中即拦截或降级 |
| 模型输出含敏感信息或恶意载荷 | 输出侧护栏二次检查，含 API Key、系统提示词时拦截 |
| 员工滥用 AI 访问未授权资源 | 工具调用风险识别 + API Key 权限分级 |
| 攻击手法不断演进，规则永远滞后 | **在线学习**：部署环境的真实流量持续喂给检测模型，能力随使用提升 |

**关键差异在最后一条。** 传统护栏是交付那一刻写死的规则表；玄盾采用「快速初筛 + 深度精判」两级结构配合正常域表征与异常检测 —— 见过的新流量会沉淀为基线，未见过的异常会被异常检测捞出来。这是「活性防护」与「静态黑名单」的本质区别。

## 二、两种交付形态

### 形态 A：Docker 集中部署（推荐）

一套命令起两个服务：网关 + 管理控制台。

```bash
# 1. 获取源码
git clone https://github.com/zhibaiYingChuan/XD.git
cd XD

# 2. 配置管理密钥（必配，否则管理端点直接拒绝访问）
export XUANDUN_ADMIN_KEY="$(python -c 'import secrets;print(secrets.token_urlsafe(32))')"

# 3. 启动
docker compose up -d

# 4. 确认网关健康
curl http://localhost:18766/health
```

启动后：

| 服务 | 地址 | 说明 |
|------|------|------|
| 安全网关 | `http://<host>:18766` | OpenAI 兼容反向代理 |
| 管理控制台 | `http://<host>:8080` | Nginx 静态控制台 |

### 管理密钥与环境变量

Docker 编排里预留了两个密钥项。**请注意它们的当前状态**：

| 变量 | 状态 | 说明 |
|------|------|------|
| `XUANDUN_ADMIN_KEY` | **后端尚未读取** | 控制台登录页依赖它，网关侧的管理端点尚未实现（见下方说明） |
| `XUANDUN_PUBLIC_KEY` / `XUANDUN_PUBLIC_KEY_PATH` | **后端尚未读取** | 编排注释中标注为必配，但 gateway 代码中无读取实现 |

> ⚠️ 建议照常设置 `XUANDUN_ADMIN_KEY`。管理端点一旦实现即刻生效，且能避免将来上线时因缺配置需重启容器。

### 形态 A 的当前限制：管理控制台尚不可用

**这是本指南必须讲清的事实，而不是需要绕过去的问题。**

管理控制台（前端）已完整实现 6 个页面：仪表盘、在线检测、审计日志、模型配置、密钥管理、系统设置。它调用两个管理端点：

| 端点 | 用途 |
|------|------|
| `GET /api/v1/stats` | 登录校验与仪表盘数据 |
| `POST /api/config/reload` | 重载配置 |

但**网关侧这两个端点目前均未实现**。当前 `docker compose up` 后：

- ✅ **网关功能完整可用** —— 检测、拦截、路由、策略、热加载全部正常
- ❌ **控制台页面能打开，但数据请求会失败** —— 登录时即报错

也就是说，**当前企业版的可用形态是「网关 + 配置文件管理」**，策略与模型通过 `config/models.yaml` 管理（见第六节），控制台待管理端点补齐后启用。

> 这正是本产品一贯的取向：接口缺失时如实报错，而不是展示假数据。控制台不会用占位内容冒充实时统计。

### 形态 B：源码安装

适合需要深度定制或已有 Python 环境的团队。

```bash
git clone https://github.com/zhibaiYingChuan/XD.git
cd XD

# Python 3.11+
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# 只装网关能力（体积最小）
pip install -e ".[gateway]"

# 或装全量（含 benchmark / tools）
pip install -e ".[dev]"
```

启动网关：

```bash
XUANDUN_MODE=protecting \
XUANDUN_ADMIN_KEY=<你的管理密钥> \
python -m daoti_xuandun.gateway.app
```

管理控制台需单独构建（React + Vite）：

```bash
cd admin-console
npm install
npm run build      # 产物在 dist/，交给任意静态服务器或 Nginx
```

## 三、把企业 AI 流量接到玄盾

玄盾网关是 **OpenAI 兼容反向代理**。接入方只需改一个地址。

### 网关提供的端点

| 端点 | 用途 |
|------|------|
| `POST /v1/chat/completions` | 对话请求（主入口，AI 工具填这个） |
| `GET /v1/models` | 模型列表 |
| `GET /health` | 健康检查 |
| `GET /api/stats/realtime` | 实时统计（控制台用） |
| `GET /api/config/safe` | 当前生效的安全配置 |
| `POST /api/rate/limit` | 设置速率限制 |

### 接入示例

在 AI 工具（Cursor、Cherry Studio、Dify 等）中：

```
API Base URL : http://<网关地址>:18766/v1
API Key      : 留空，或任意占位值（见下方说明）
```

原来填 `https://api.openai.com/v1` 的地方，改成 `http://<网关地址>:18766/v1` 即可。**其余配置（含模型名）一律不动。**

> ⚠️ 许多 AI 工具不允许 API Key 为空，此时填任意占位字符串即可。

### ⚠️ 入站请求当前不做鉴权 —— 部署前必读

**网关不会校验调用方身份。** 真实后端 Key 由网关从 `XUANDUN_MODEL_<ID>_KEY` 环境变量读取并注入转发，调用方看不到也无需持有它。

这意味着：**任何能访问到 `<网关地址>:18766` 的客户端都可以使用你的后端额度。**

因此部署时务必：

- ✅ 把 `18766` 绑定到内网地址，**不要暴露到公网**
- ✅ 在网关前置一层认证（Nginx basic auth、企业 VPN、mTLS，或用 iptables 限制来源 IP）
- ✅ 确认后端 Key 的额度与告警阈值

网关侧的企业 Key 签发与验签能力（`XUANDUN_PUBLIC_KEY`）目前**尚未实现**，控制台的「密钥管理」页面依赖它，因此暂不可用。

### 业务侧调用示例

```bash
curl http://<网关地址>:18766/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt4o",
    "messages": [{"role": "user", "content": "帮我总结这份季度报表"}]
  }'
```

- 正常 → 返回模型响应
- 命中风险 → HTTP `403`，响应体说明拦截原因
- 令牌不认识的 model → 按配置报错或走 fallback（若配置了）

## 六、配置检测策略

企业版的策略**不在环境变量里，而在 `config/models.yaml`**。网关启动时读取，改动会被 watchdog 监听并热加载（防抖 500ms），无需重启。

### 安全策略档位

| 档位 | 适用 | 说明 |
|------|------|------|
| `strict` | 高敏感行业 | 误报换漏报为零的取向 |
| `balanced` | 默认 | 误报与漏报折中 |
| `permissive` | 内部已充分基线 | 少打扰，正常业务表达优先 |

### 全局默认配置

默认从 `config/models.yaml` 读取（可用 `--config` 指定其他路径）：

```yaml
# config/models.yaml
version: "1.0"

default:
  security_policy: balanced   # strict / balanced / permissive
  audit_log: false            # 是否写审计日志
  timeout_seconds: 300        # 转发到后端的超时

models: []
routes: []
```

**改完即可生效** —— 网关会自行加载，不需要重启容器。

### 单个模型的策略覆盖

`models` 与 `routes` 为空时，网关只做透传与健康检查，不做路由决策。要启用完整能力，需声明后端模型：

```yaml
models:
  - id: gpt4o
    display_name: GPT-4o
    provider: openai
    backend:
      provider: openai
      model: gpt-4o
      base_url: https://api.openai.com/v1
      api_key_env: XUANDUN_MODEL_GPT4O_KEY   # 必须是这个命名规范
    security:
      input_check: true          # 输入检测
      output_check: false        # 输出检测
      policy: balanced
```

> ⚠️ `api_key_env` 有强制命名规范：`XUANDUN_MODEL_<MODEL_ID>_KEY`。写错会在配置加载时直接报错，而不是静默失效。
>
> ⚠️ 配置声明了但对应环境变量未设置的模型，网关会**自动标记为 disabled** 并在启动日志中逐条报告 —— 不会静默尝试调用然后失败。

### 路由规则

`routes` 支持按 `model` 或 `header` 匹配（**二者只能选其一，model 优先**），用于把不同请求导向不同模型：

```yaml
routes:
  - match:
      model: gpt4o          # 精确匹配；写 gpt* 前缀通配
    target_model_id: gpt4o
```

配置需满足：目标 `model_id` 必须在 `models` 中存在；`fallback` 不得成环。

## 七、运维要点

### 持久化

Docker 部署已配置两个卷，重建容器不丢数据：

| 卷 | 用途 |
|----|------|
| `xuandun-logs` | 审计日志 |
| `xuandun-data` | 运行时状态（吊销名单等） |

> ⚠️ `xuandun-data` **不可**挂到 `/app/gateway` 源码目录，否则会覆盖镜像内代码，导致每次重建都在跑旧版本。

### 健康检查

```bash
curl http://<网关地址>:18766/health
```

容器已配 healthcheck（间隔 30s，超时 5s，重试 3 次），`docker compose ps` 可直接看状态。

### 日志

```bash
docker compose logs -f xuandun-gateway
```

## 八、常见问题

**Q：管理控制台能登录吗？**
A：**目前不能。** 控制台依赖的 `/api/v1/stats` 与 `/api/config/reload` 两个管理端点在网关侧尚未实现，登录时即会失败。当前请用 `config/models.yaml` 配置策略（支持热加载）。这是已知的功能缺口，不是部署错误。

**Q：控制台页面打得开，是不是装好了？**
A：页面打得开只说明静态资源部署正常。数据请求会失败 —— 界面会明确报错，不会用占位内容冒充数据。

**Q：控制台的「密钥管理」能用吗？**
A：**暂时不能。** 企业 Key 的签发与验签依赖尚未实现的后端能力。调用方也不需要企业 Key —— 网关用环境变量里的后端 Key 转发（见「入站请求当前不做鉴权」）。当前的管控手段是网络层隔离。

**Q：`XUANDUN_ADMIN_KEY` 要配吗？**
A：建议配上。网关侧管理端点尚未实现，但设置后可在端点实现时即刻生效，避免将来需重启容器。

**Q：策略改了要重启吗？**
A：不需要。网关用 watchdog 监听 `config/models.yaml`，防抖 500ms 后自动热加载。

**Q：模型配了但调不通？**
A：检查两点 —— ① `api_key_env` 必须符合 `XUANDUN_MODEL_<ID>_KEY` 规范，写错会在加载时直接报错；② 对应环境变量必须已设置，未设置的模型会被**自动标记为 disabled** 并在启动日志中逐条报告。

**Q：误报太多？**
A：把 `policy` 调低一档（`balanced` → `permissive`），或对特定模型单独覆盖 `security.policy`。累积一段真实流量后基线会更准。

**Q：检测命中返回什么？**
A：HTTP 403。响应体说明拦截原因。

**Q：能只用网关不部署控制台吗？**
A：可以，且**这是当前推荐的形态**。控制台尚未可用，网关功能不受影响。

**Q：性能开销？**
A：网关增加一跳网络延迟与检测计算。检测强度与延迟是权衡项，见 [benchmarks.md](benchmarks.md) 实测数据。

## 九、能力边界（请如实评估）

**必须说清的四件事：**

1. **入站请求当前不做鉴权。** 网关不校验调用方身份，任何能访问该端口的客户端都能消耗你的后端额度。**部署必须配合网络层隔离**（见第三节）。

2. **玄盾是活性防护，不是绝对防护。** 检测能力随部署环境的学习逐步提升。文档与基准报告中的数据**仅反映对测试集的统计表现，不代表对未知或新型攻击的绝对防御能力**。

3. **管理控制台当前不可用。** 前端已完成，但依赖的两个管理端点尚未实现。当前请用 `config/models.yaml` 管理策略。

4. **检测存在漏报可能。** 未知攻击形态、刻意构造的规避、加密或分片传输，都可能绕过检测。安全是过程，不是终点。
